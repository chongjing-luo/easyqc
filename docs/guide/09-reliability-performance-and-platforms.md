# EasyQC 可靠性、性能与平台边界

## 1. 可靠性的目标

EasyQC 的主要风险不是远程服务不可用，而是本地写入中断、两个进程同时改同一项目、评分文件被混放，以及大表操作冻结 GUI。当前设计围绕四个原则：

1. 权威 JSON/CSV 只在完整候选准备好后发布；
2. 同一项目并发写入明确失败，不静默覆盖；
3. 身份与 schema 错误阻止聚合，不输出残缺结果；
4. 完整数据计算可以较重，但 Qt 控件更新只留在 GUI 线程。

## 2. 原子发布

项目设置和评分写入采用同目录唯一临时文件：

```text
serialize candidate
→ write unique temporary file
→ flush
→ fsync file
→ os.replace target
→ fsync relevant directory where required
```

`os.replace` 使同一文件系统上的读者看到旧完整文件或新完整文件，而不是半段 JSON。若序列化、权限或 replace 前失败，现有目标保持不变。

“原子”在这里是本地文件发布语义，不等同于数据库多表 ACID 事务，也不承诺网络文件系统、同步盘或跨机器缓存具有相同行为。

## 3. 表格修订与 CAS

`easyqc_all.csv` 写入除临时文件替换外，还使用 SHA-256 修订作为 compare-and-swap（CAS）条件：

1. GUI/后台任务捕获当前表修订；
2. 用户准备候选变更；
3. 提交前重新核对磁盘修订；
4. 若另一个操作已改变文件，当前候选失败；
5. 用户刷新后基于新版本重做操作。

这避免后台 Formula、导入或删除操作把更晚的名单更新覆盖掉。

## 4. 项目级写锁

权威写入使用两层锁：

- 进程内可重入互斥锁，协调同一 EasyQC 进程中的任务；
- 非阻塞操作系统文件锁，协调同一机器上多个 EasyQC 进程。

跨进程锁竞争时操作立即明确失败，而不是无期限等待。锁覆盖评分及与模块身份相关的设置变更，防止“模块刚改名，旧身份评分同时写入”的竞态。

这些锁不是分布式锁。不要让多台机器同时写同一个 NFS/SMB/云同步项目目录；当前产品定位是本地工作站，而不是多用户服务器。

## 5. 身份与文件系统防线

评分安全不仅依赖文件名：

- module/rater/easyqcid 先经过可移植字符和长度校验；
- 规范文件名有 UTF-8 字节预算；
- 绝对目标有 Windows 路径预算；
- 目录、文件名和正文三处身份必须一致；
- 写入前检查大小写折叠冲突；
- 扫描不跟随符号链接；
- 重复三元身份使聚合失败。

这些检查牺牲了任意 Unicode 文件名，换取 Linux、Windows 和 macOS 之间更稳定的路径可移植性。

## 6. 表格性能策略

EasyQC 的常规目标是约不超过 100,000 行、约 300 列、16 GiB 工作站。核心策略包括：

- pandas 持有完整数据；
- 筛选和排序返回源位置数组，而不是复制完整结果表；
- Qt model 只暴露当前页窗口；
- 固定列和普通列共享行窗口；
- 导出按块写入；
- 长任务通过后台控制器运行；
- 返回时用上下文/数据修订拒绝过期结果。

这不是无限规模承诺。行数、列类型、文本长度、筛选表达式、评分文件数量、磁盘速度和同时存在的 DataFrame 副本都会影响内存与延迟。

## 7. 已保留的性能证据

以下数字只说明特定修订和合成环境下通过了预声明门槛。

| 工作负载 | 结果 | 门槛 | 证据位置 |
|---|---:|---:|---|
| 100,000 个真实 schema-v3 评分 JSON 的扫描、校验、展平、透视和合并 | 30.628661 s；峰值 1555.043 MiB | ≤60 s；<4096 MiB | `dev/archive/easyqcid-schema-v3-audit-remediation/` |
| 100,000×300 合成名单查询 | p95 119.919 ms；Qt application delay 89.883 ms；峰值 859.859 MiB | 查询 p95 ≤500 ms；RSS ≤4096 MiB | `dev/archive/module-qc-filter-usability/` |
| 100,000×300 合成名单 Formula | 0.895 s；峰值 698.375 MiB | <10 s；<4096 MiB | `dev/archive/easyqc-formula/` |

### 7.1 不能从这些数字推出什么

不能据此声称：

- 所有真实 100,000 行项目都在相同时间内完成；
- Windows/macOS 与测试 Ubuntu 性能相同；
- 网络盘、机械盘和本地 SSD 相同；
- 任意模块/质控员数量、任意 JSON 形状都相同；
- 外部查看器启动或原生 Qt 绘制包含在 Core benchmark 中；
- 16 GiB 对所有数据都一定足够。

论文只能将它们表述为 revision-bound synthetic benchmarks，并同时报告数据形状、环境和限制。

## 8. GUI 响应性

项目加载、结果刷新、Formula 完整提交、模块筛选保存和 CSV 导出通过后台任务运行。GUI 线程负责：

- 更新 Qt 控件；
- 显示 busy/错误状态；
- 应用仍属于当前上下文的结果；
- 拒绝用户重复触发冲突动作。

线程化并不使 pandas 运算更快；它的目标是让窗口可以绘制和响应，并防止旧项目任务回写新项目。

## 9. 跨平台 GUI 策略

当前 UI 稳定性依靠：

- Qt layout 与 size policy，而不是绝对坐标；
- 标准 Qt 控件和原生窗口边框；
- 操作系统字体与 DPI 缩放；
- 有边界的语义 light QSS，只定义角色、间距和状态；
- 表格按内容/策略分配列宽并保留滚动条；
- 不捆绑固定字体、不绘制自定义标题栏、不追求像素级一致。

目标是不同平台都不重叠、不截断、可滚动、可操作，而不是三张截图像素完全相同。系统字体不同导致字宽和控件高度略有差异是预期行为。

## 10. 双语切换

左侧导航底部只有一个目标语言按钮：中文界面显示 `English`，英文界面显示“中文”。切换即时应用并持久化选择，不重建项目业务状态。

翻译边界是应用自有 UI 文本。以下用户数据不会被翻译：

- 项目名；
- 模块名和 label；
- rater 与 `easyqcid`；
- 用户定义的评分、标签和列名；
- 路径、命令、备注和表格单元格。

这避免切换语言改变数据身份或研究语义。

## 11. 当前平台证据

### 11.1 自动化矩阵

仓库 `.github/workflows/qt-platform.yml` 定义四行 offscreen Qt 验证：

- Ubuntu 22.04 x86_64；
- Ubuntu 24.04 x86_64；
- Windows Server 2022 x86_64；
- macOS 15 arm64。

该矩阵验证导入、Core/Qt 合同和平台探针，但 `QT_QPA_PLATFORM=offscreen` 不等于真实桌面人工验收。

### 11.2 原生目标合同

当前目标平台是 Ubuntu 22.04/24.04 x86_64、Windows 11 x86_64 和 macOS 13+ arm64。Ubuntu 是最充分的本机使用证据。Windows/macOS 的真实 DPI、多显示器、辅助技术、字体回退、原生文件对话框以及实际神经影像查看器组合仍需在目标机器上验收。

因此应说“同一 Qt 实现和自动化矩阵已覆盖三大平台”，不能说“所有平台原生 UI 和查看器已经完成验证”。

## 12. 日志退化策略

日志目录按以下顺序选择：

1. 若 `EASYQC_LOG_DIR` 是有效绝对路径，使用它；
2. 否则使用 platformdirs 的用户日志目录。

文件名为 `easyqc_YYYYMMDD.log`。若文件日志无法创建，程序保留控制台日志并在 Qt 启动后显示一次警告；不会因为日志目录权限问题使整个应用无法启动，也不会静默失去可观察性。

## 13. 发布前平台测试建议

每个真实目标系统至少验证：

1. 全新 `.venv` 安装和 Qt 启动；
2. 系统字体、100%/150%/200% DPI 和多显示器；
3. 七个导航页、折叠菜单和中英文切换；
4. 100k 代表性名单的滚动、筛选、Formula 和导出；
5. 目标实验室实际 viewer command；
6. 保存、覆盖、右键复查和结果聚合；
7. 无写权限、并发写锁、坏 JSON 等失败路径。

Linux 本机测试不能证明 Windows/macOS；后续可使用 VM 验证 Windows，但 macOS arm64 最终仍需要真实 Mac 或等价合规硬件。
